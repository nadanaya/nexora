# A04 설계 설명 초안 — NEXORA

작성 기준: 제공 A04 v1.5(2026-10-29), W07, A01·A05, 공통 승인 정책. 검증일 2026-11-10. **외부 AI 실호출은 미연결이며, 이 항목은 보완 후 제출해야 합니다.**

## 1. 문제와 전문성 확장 요약

**결과물 이름:** NEXORA — 관련 거래처 판매장려금 지급 통제 플랫폼.

**선택한 사용자·의사결정:** Corevia 영업지원팀이 월 장려금 요청을 심사하고, 관련자 합산 한도에 따라 영업임원이 최종 승인하며, 재무팀이 승인된 요청을 일정에 반영해 모의 지급하는 업무입니다. 영업팀은 관계와 정산·계좌 증빙을 소명합니다.

**현재의 어려움:** 거래처별 금액만 보면 각 건이 200만 원 이하라도 관련자 그룹 합계는 한도를 넘을 수 있습니다. 승인 당시의 관계 정보, 합산 근거, 소명, 실제 지급 수취계좌가 분리되어 있으면 정정 후에도 예전 승인으로 지급하는 문제가 생깁니다. 원본에는 당시 마스터 이력과 그룹 합산 승인서, 실제 지급 수취계좌 증거가 충분하지 않습니다.

**기업 운영 안에서의 연결:** 거래처 마스터·장려금·입금 이력으로 관계와 월 합계를 확인하고, 영업 소명과 승인 심사를 거쳐 재무 일정과 지급 기록으로 연결합니다. 회수계좌는 소명 신호로 다루고 지급 수취계좌로 추정하지 않습니다. 승인 완료만 화면에 표시하는 대신 지급 실행 가능 조건을 다시 확인하고 상태와 감사 이력을 함께 저장합니다.

**주업무의 시작과 종료:** 거래처·정산 월 기안에서 시작하여 관계 조회·합산·증빙 보완·사람 승인·일정 반영·모의 지급 영수증과 감사 이벤트 생성까지 처리합니다. 정보 부족이나 거절은 지급 완료로 종료하지 않고 확인·보완 작업으로 이어집니다.

**관심·전문성 관점:** 관계 그래프와 상태 전이, 동시성·멱등성 같은 소프트웨어 통제 관점을 적용했습니다. 개인의 별도 경력이나 기업 실무 경험을 가정하지 않습니다.

**필수 전문성 확장:** 관계 변경 영향 분석입니다. 마스터 정정의 적용 전후 연결요소·그룹 합계·필요 승인 권한·영향 심사를 계산합니다. 변경된 그룹의 기존 승인을 무효화하고 일정을 중지하며, 합병·분리 시 새 심사를 생성합니다. API B와 브라우저 B에서 240만 원 그룹이 90만 원 거래처로 분리되고 승인 권한과 다음 처리 경로가 달라지는 것을 확인했습니다.

**다른 부서의 목표·제약과 실제 반영:** 영업팀은 근거가 확인된 회신을 제공해야 하며, 제출만으로 검토 완료가 되지 않습니다. 재무팀은 유효한 사람 승인과 검증된 지급 계좌가 있는 건만 일정에 반영합니다. 보류·취소·정보 정정은 일정을 중지하고, 재심사 거절은 기존 일정을 취소합니다. 영업 작업 완료와 지급 일정의 변경을 자동 테스트·브라우저 C에서 확인했습니다.

**확인할 개선 효과:** 합산 누락, 무증빙 지급, 동일인 승인, 오래된 승인 재사용, 중복 지급 시도를 차단하는지 비교합니다. 원본의 과거 기록은 사후 검토 신호로 설명하며 부정이나 승인 부재를 확정하지 않습니다. 실제 금전 절감·생산성 개선 비율·사기 적발 실적은 측정하지 않았습니다.

## 2. 업무모델과 데이터 설명

**객체:** 거래처와 마스터 버전, 관련자 그룹과 직접 간선, 장려금 항목, 심사 회차, 증빙·검토, 승인, 부서 작업, 재무 일정, 모의 지급 영수증, 감사 이벤트입니다.

**관계:** 대표자·주소·등록 정산계좌 중 빈 값/NONE을 제외한 두 항목 이상이 정확 일치하면 직접 연결하고, NetworkX 연결요소로 전이 그룹을 구합니다. 기본 정규화는 Unicode NFC와 앞뒤 공백 제거입니다. 유사한 이름이나 주소라는 이유만으로 확정 간선을 만들지 않습니다.

**상태·시점·담당·권한:** 가상 기준일은 2026-07-01, 정산 월은 지급일과 구분합니다. DRAFT→증빙 검증→영업지원 승인 대기→필요시 영업임원 승인 대기→승인 완료→일정 반영→모의 지급으로 이동합니다. 보류·거절·재심사·대체 심사는 별도 상태입니다. 기안자와 승인자를 분리하고 서버의 로그인 사용자·등록 역할로 권한을 확인합니다.

**규칙과 제약:** 월 그룹 노출액이 2,000,000원을 초과하면 영업임원의 최종 승인이 필요합니다. 영업지원 중간 승인만으로 지급하지 못합니다. 현재 버전·관계·금액·증빙·수취계좌에 묶인 승인만 사용합니다. 이미 지급한 원본 항목은 신규 기안에서 제외하고 성공 지급 항목에는 DB 유일 제약을 둡니다. 지급 전 재검증과 상태·지급 항목·감사 저장은 하나의 PostgreSQL 거래에서 실행합니다.

**BPMN 변경:** W07의 영업지원 검토→사람 승인→회계 지급 흐름에 필수 증빙 보류, 분리 승인, 정정 영향 미리보기·재기안, 취소·거절에 따른 일정 조정, 재시도 통제를 구체화했습니다. 지급 수취계좌 검증과 기안자 분리는 참가자가 추가한 통제이며 원본 정책을 삭제하거나 한도를 높이지 않았습니다.

**AI·사람·도구의 연결:** AI 입력은 마스킹된 관계 근거와 서버 계산, 부족 증빙이며 출력은 구조화 설명과 부서 작업 제안입니다. 근거 키와 스키마를 검증하고 실제 규칙 결과는 서버에서 첨부합니다. AI에 승인·지급 변경 도구를 주지 않습니다. 현재는 실제 모델 자격 증명이 없어 이 설명 단계의 외부 호출은 차단입니다. 형식·오류·근거 검증은 모의 응답으로 확인했으며, 모의 결과를 운영 AI 성과로 서술하지 않습니다.

AI가 실제 생성한 근거를 담당자가 검토한 후 승인하는 전체 A 흐름은 외부 모델 연결 후 다시 시연해야 합니다. 현재 시연은 그 단계의 차단과 이후 결정론적 업무 흐름을 나누어 보여줍니다.

## 4. 추가 확장 목록

- **관계 변경 영향 분석:** 전후 그룹·금액·권한 차이와 재기안·일정 중지까지 실제 구현·검증했습니다.
- **지급 동시성·멱등 통제:** 같은 요청 재시도와 다른 키의 중복 지급, 취소와 지급의 경합을 실제 PostgreSQL에서 검증했습니다.
- **AI 근거·실패 통제:** 구조화 출력·허위 근거·금액 실행 필드 삽입 차단과 실패 감사는 구현·모의 검증, 외부 실호출은 미검증입니다.
- **과거·미래 시점 그래프 및 실제 은행 연동:** 현재 범위에 없으며 설계 가능성을 실행 완료로 표시하지 않습니다.

## 5. 실행·재현 방법

프로젝트 README, [시연 순서](DEMO_GUIDE.md), [최종 검증표](FINAL_VALIDATION.md), backend/openapi.json을 함께 제공합니다. Python 3.12·PostgreSQL 18 설치 환경에서 임시 DB 검증을 수행했고 React/TypeScript/Tailwind와 FastAPI/NetworkX를 사용합니다.

`python scripts/test-postgres.py`는 독립 DB에서 전체 테스트를 실행합니다. `python scripts/demo-server.py`와 `python scripts/demo-api.py all`은 새 합성 자료로 HTTP 시연을 재현합니다. 브라우저는 로컬 시연의 합성 역할 전환을 사용합니다. `snapshot`으로 상태·작업·지급·감사·DB 행 수를 저장하고 `stop`으로 해당 환경만 종료합니다. 운영 앱의 원본·과거 지급·승인 데이터는 초기화하지 않습니다.

검증 자료는 submission/evidence에 있습니다. 외부 AI를 추가하려면 AI_SETUP.md의 서버 환경변수 세 가지를 설정하고 실제 모델 테스트와 A 전체 시연을 다시 수행해야 합니다. 키를 제출 소스에 포함하지 않습니다.

## 6. 제출 전 자기점검

업무 객체·관계·권한·상태 전이, 원본과 합성의 구분, 필수 확장·다른 부서 영향, 정상·변경·부족·거절·동시성 증거를 연결했습니다. 실제 작동·모의 입력·미구현 부분을 구분했습니다. **외부 AI 실제 운영 항목은 아직 충족했다고 주장하지 않습니다.** 실제 제출 일정·제출처·형식은 별도 운영 공지에서 확인해야 합니다.
